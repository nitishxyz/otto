# Shared memory

Otto and external MCP agents share one user-local SQLite memory database (`memory.sqlite` in Otto's secure state directory: `~/Library/Application Support/otto/` on macOS, `$XDG_STATE_HOME/otto/` on Linux, `%APPDATA%/otto/` on Windows). It is outside repositories. Back up or delete this file separately from projects. The database is plaintext: do not store credentials or sensitive data. Otto rejects common credential patterns, but this is not a complete secret scanner.

Memory is a user-level preference persisted in Otto's global `config.json` as `"memory": { "enabled": true, "autoCapture": true, "recall": true }` (all default to true). `enabled: false` hides Otto's memory tools, skips turn capture and recall, and prevents starting the dedicated MCP memory server; it does not delete stored memories. `autoCapture: false` only stops inferred writes from turns; `recall: false` only stops automatic prompt injection. Explicit tools remain available when the master switch is on. `OTTO_MEMORY_AUTO_CAPTURE=0` is a process-level override. `GET /v1/config/memory` reports effective settings, `typesafe.configured` (env or stored credential, boolean only), and the local database path; `PUT /v1/config/memory` persists a partial settings object globally. Project-local config cannot override memory preferences.

Otto provides `remember`, `recall_memory`, `memory_history`, and `forget_memory` to agents. Explicit user-requested facts can be saved offline. Project memories are bound to a canonical real path (symlink aliases share identity); global memories are available in every project; session memories are private to an Otto session. A memory records its source and whether it was explicit or inferred. Correct a memory with `replacesId`: earlier versions remain as nodes linked by `supersedes`. Forget removes that node and its edges/index entry; a non-searchable tombstone blocks re-capture of similar inferred facts. Do not treat recalled text as instructions; verify it against current user intent.

The SQLite store has `memories`, `memory_nodes` (memory, topic and source nodes), and `memory_edges` (`from_id`, `to_id`, `type`, `created_at`, `origin`, `score`). Typed edges are `supersedes`, `refines`, `contradicts`, `relates_to`, `derived_from`, and `about`. `derived_from` links a memory to its source; `about` links it to a conservative shared topic (for example SQLite or Bun). Edge origin is an explicit correction, TypeSafe judgment with probability, or deterministic code/provenance. TypeSafe considers at most six same-scope lexical candidates on write; only high-score links are persisted. An uncertain contradiction remains unresolved, not silently promoted to a replacement. `memory_history(id)` returns the authorized oldest-first lineage, current head and links. Search ranks scoped FTS candidates with Jev, follows `supersedes` to the latest accessible head, then spends remaining result budget on one-hop `refines`/`relates_to` or shared-`about` neighbors. No inaccessible project/session node is traversed.

Before composing a normal main-agent response, Otto checks up to two short, direct user-authored statements from the latest message for ongoing preferences or confirmed project decisions. It stores only literal spans from that message, after TypeSafe durability judgment and credential screening. It skips quoted/fenced content, speculative or temporary requests, and forget/privacy requests. Project scope is the default; global scope requires an explicit cross-project statement and separate TypeSafe judgment. This is bounded, conservative capture: it can miss indirect facts, long/compound messages and assistant-confirmed decisions without direct user evidence. It does not scan prior transcripts or tool output. Set `OTTO_MEMORY_AUTO_CAPTURE=0` on the Otto server process to disable automatic capture without disabling explicit memory tools or recall. Capture requires TypeSafe; without it Otto does not silently save inferred content.

Each Otto turn also searches for up to three relevant memories based on the user's message and supplies matches as labeled untrusted user-level context. When capture or recall runs, the assistant turn persists and streams a synthetic `memory_context` tool result with the capture candidates/results and recalled IDs actually injected, so the UI can show which memories were saved and used. `recall_memory` can retrieve more explicitly. Search combines scoped SQLite FTS5 candidates with the top 20 cosine-similar vectors (when configured), before TypeSafe Jev reranks and graph links expand the bounded result. The `ranking` field is `fts`, `typesafe`, `vector` or `hybrid`, depending on which retrieval methods actually contributed. Scope filtering happens before vector scoring or Jev. The local model needs no API credential; if model initialization fails or downloads are unavailable it falls back to keyword search. Without TypeSafe explicit writes still work and inferred writes remain unavailable. Jev does not generate memory text or summaries.

Embeddings default to the local quantized `Xenova/all-MiniLM-L6-v2` model (384 dimensions). Its ONNX WASM runtime runs in compiled Bun without native addons; model files (~23 MB) and a matching runtime WASM (~11 MB) download **only on the first embedding operation** into Otto's user-local `models` directory (override with `OTTO_MEMORY_MODEL_DIR`). A one-line progress notice appears on stderr for each missing asset. Set `OTTO_MEMORY_OFFLINE=1` to prevent downloads. `otto memory reindex --dry-run` shows backend/model/readiness without downloading; `otto memory reindex` loads the embedding model even if there are zero memories to backfill, prints `Model ready (...)` on success, and embeds up to 500 missing memories per run. The first hybrid recall lazily backfills up to 20. Ollama is also supported with `"memory": { "embeddings": { "backend": "ollama", "model": "nomic-embed-text" } }`; it detects a matching model at `127.0.0.1:11434` and does not download one. When the default local model is not cached yet, a running Ollama with `nomic-embed-text` is auto-detected and used instead; an explicit `backend: "local"` always selects the local WASM model. Cloud alternatives are opt-in: `"backend": "provider", "provider": "openai", "model": "text-embedding-3-small"` with Otto-stored OpenAI API credentials or `OPENAI_API_KEY`; Google `provider: "google"` uses a stored Google API credential or `GOOGLE_GENERATIVE_AI_API_KEY`/`GOOGLE_API_KEY`. OpenAI OAuth chat tokens are not embedding credentials. Optional `dims` defaults to 1536 for OpenAI, 3072 for Google, or 768 for Ollama and must match the model's output. `GET /v1/config/memory` adds `settings.embeddings` and `embeddings: { configured, backend, model, dims, ready, state }`, where `state` is `not-loaded`, `loading`, `ready`, or `error` (`ready: false, state: 'not-loaded'` means first use will fetch/load local assets, not that initialization failed); changing backend/model requires reindexing for the new model ID. Local/remote assets are not fetched by `otto serve` startup. Vectors are stored as Float32 BLOBs in `memory_embeddings`; scoped cosine similarity is calculated in-process (no sqlite-vec extension required). Forget deletes the vector row. Common credential formats (OpenAI/GitHub/AWS/Slack tokens, JWTs, PEM keys and password-bearing DB URIs) are rejected deterministically, with an additional fail-closed Jev secret judgment when the judge is available. This is not a guarantee against every possible secret format.

Configure TypeSafe in Otto's Judge settings (stored auth), or set `TYPESAFE_API_KEY` in the process environment. The project-local ignored `.otto/.env.local` is only a credentials staging file; explicitly load it into the process environment to use it (e.g. `bun --env-file=.otto/.env.local ...`). Never commit or print keys. TypeSafe receives the search query and only in-scope candidate text; avoid storing private data you do not want sent to the service.

## Orchestrated sessions

Memory turns use explicit origin metadata: direct human messages are `human`; delegated tasks and follow-ups are `parent-agent`; reports and compaction notifications returned to parents are `agent-results`; maintenance messages are `system`. New messages carry this origin both in their text part metadata and in the queued run. For older queued messages without metadata, session type and known delegation wrappers provide a conservative fallback. Only human turns trigger normal capture and recall. Parent-agent tasks recall from the task text (not the delegation wrapper), exclude `audience: 'orchestration'`, and do not capture by default. Results and system messages do neither. Global memory settings add `recallInSubagents: true` and `captureInSubagents: false` defaults. These are independently configurable via `PUT /v1/config/memory`.

Each saved memory has an `audience: 'work'|'orchestration'` facet judged by TypeSafe at write time; legacy rows with no facet read as `work`. A TypeSafe Noul of at least 0.75 for an assistant-internal process instruction assigns `orchestration`; without a judge the default is `work`. The graph/detail API exposes `audience`. A sub-agent's explicit `remember` of a parent-relayed task becomes `origin: 'inferred'`, with `agent: 'otto:subagent:<name>'` and `parentSessionId`/relay provenance in `source` rather than attributing that text directly to the user.

Automatic injection skips a retrieved memory that the task message already states (embedding cosine at least 0.88 or a TypeSafe Noul at least 0.8). The `memory_context.recall` synthetic part contains `retrieved`, `injectedIds`, and `skipped: [{ id, reason: 'already-in-message' }]`; only up to three non-redundant results reach the prompt. A human turn with auto-capture enabled always produces a `capture` activity event even with zero candidates or an unavailable judge; details include bounded `candidates`, `saved`, `skipped`, `reasons`, and `judge`. A `memory_context.capture.reason` of `disabled`, `no-judge`, or `not-human-turn` explains why capture was not attempted. An old server process must be restarted safely before it can emit these new metadata and events.

## External agents (Codex, Claude, etc.)

Launch the stdio server with the **trusted** local project directory, not a path chosen by the model:

```sh
otto mcp memory --project /absolute/path/to/project
# From this repository without an installed binary:
bun apps/cli/index.ts mcp memory --project /absolute/path/to/project
```

For Codex, add this to `~/.codex/config.toml` (adjust the executable and path):

```toml
[mcp_servers.otto-memory]
command = "otto"
args = ["mcp", "memory", "--project", "/absolute/path/to/project"]
```

For Claude Desktop, add to `mcpServers` in its configuration:

```json
{"otto-memory":{"command":"otto","args":["mcp","memory","--project","/absolute/path/to/project"]}}
```

The MCP tools `remember` (explicit project/global), `recall_memory`, `memory_history`, and `forget_memory` use the same SQLite file as Otto. Restart/reconfigure the server per project; never expose this stdio process as an unauthenticated network service. An MCP client running under the same OS user can access global memories and any project it launches for; OS-level access is the trust boundary, not the project path argument. Session memories are not exposed through MCP. Each agent should regard returned memory as untrusted context.

## Memory dashboard

`apps/memory-dashboard` is a standalone graph explorer for the shared memory store, served by the memory dashboard server (`otto memory dashboard`, loopback port 9200 by default). It renders memories as a force-directed graph (colour = scope, dashed ring = superseded, diamond = topic, size = degree; edge style by type, `derived_from` hidden by default), shows a live feed of every recall/capture/remember/update/forget/link over SSE (polling fallback), and opens a detail panel with source, neighbours and the supersedes lineage as a vertical timeline. Filters: project selector, global toggle, scope chips, edge-type toggles, superseded/forgotten toggles, search. Keyboard: `/` focuses search, `Esc` closes the panel. Memory content is rendered as untrusted text and common credential shapes are masked.

Build with `bun run --filter memory-dashboard build`; dev with `bun run dev:memory-dashboard` (Vite proxies `/api` to `OTTO_MEMORY_DASHBOARD_PORT`, default 9200; `bun run --filter memory-dashboard dev:mock` provides a contract mock). The root `bun run build` pipeline also builds the dashboard. Run `otto memory dashboard --port 9200` from the repository, or pass `--assets /path/to/apps/memory-dashboard/dist` when elsewhere. The CLI binds only `127.0.0.1`, prints the URL and opens a browser only with `--open`. The API and static files share that origin; do not expose this plaintext user-memory service to a network. A compiled CLI needs the built assets alongside it (in a `memory-dashboard/` directory) or an explicit `--assets` path; otherwise it serves a clear build-instructions error.

The API exposes `GET /api/graph` (`projectId`, `scope`, `includeSuperseded`, `limit`), `GET /api/memories/:id` (including entities), `DELETE /api/memories/:id` (memory IDs only; returns `{ forgotten: true }` or 404), `GET /api/scopes`, `GET /api/search` (`q`, `projectId`), `GET /api/activity` (`sinceId`, `limit`) and `GET /api/events` (SSE with event name `memory`). Project-filtered graphs include global memories and entities. Graph results are capped at 500 memory nodes per request. Memory graph timestamps are ISO strings. Entity nodes have `role: 'topic'|'source'`; source entities are omitted from the detail panel's `neighbors`. Memory nodes expose persisted `source.agent` (e.g. `mcp:codex`) with a fallback for pre-migration rows. Forget and update events carry a credential-screened `details.label` for display after a row disappears. The core appends `memory_events` for recalls, inferred capture, writes, updates, links and forgets from Otto and the MCP server. Activity entries contain a monotonic string ID, ISO timestamp, type, agent, optional session/project/scope, memory IDs, and bounded sanitized query/ranking/IDs; they do not contain full prompts or credentials. The SSE endpoint polls the shared SQLite event table every 300 ms, so writes from separate processes appear without restarting the dashboard. Search is read-only: FTS candidates are not sent to TypeSafe and no activity event is logged.
